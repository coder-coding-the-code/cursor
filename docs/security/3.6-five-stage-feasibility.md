# 3.6 五阶段语义防火墙：可行性评估

> 评估对象：以「预处理 → 规则扫描 → 结构/RBAC → 本体校验 → 轻量语义分类」为核心的语义管道漏洞过滤器。  
> 对应需求：**每一条语义消息必须过墙**，覆盖 Prompt Injection、本体投毒、恶意语义结构、越狱、隐藏指令、权限提升、语义混淆、工具滥用。  
> 结论口径：**需求可行，架构可立项；不能把五阶段流水线当成 3.6 的充分条件。**

---

## 0. 结论（先看这张表）

| 判定 | 口径 |
| --- | --- |
| **总体** | **可行**。五阶段是正确的分层思想（先确定性、后语义；先内容、后权限；先形状、后推理），可以作为 ECS Semantic Firewall 的第一代强制闸门。 |
| **作为唯一安全控制** | **不可行**。文本分类过了 ≠ 工具可以执行；本体一致 ≠ 本体可信任。权限与副作用必须在模型外强制。 |
| **作为 3.6 的完整实现** | **部分可行**。入站文本威胁（隐藏指令、已知越狱、混淆、直接注入）覆盖强；工具回执间接注入、多轮目标劫持、MCP 工具投毒、逻辑一致的本体投毒覆盖不足。 |
| **建议** | **GO，带约束**：保留五阶段作热路径；补「动作面 / 出站面」复用同一套阶段，而不是再堆第六个黑盒模型。 |

一句话：

> 这套方案**能做成语义防火墙，不能做成语义杀毒软件**。防火墙的价值是强制 choke point + 失败默认 + 权限与本体变更 fail-closed；不是把所有隐晦意图都分类出来。

---

## 1. 需求拆解：3.6 真正在要求什么

3.6 有两层要求，常被画成一张流水线图后混在一起：

| 层 | 要求 | 五阶段图有没有覆盖 |
| --- | --- | --- |
| **强制闸门** | 每条语义消息必过过滤器；不可由模型自行豁免 | 图上有「阻断 / 放行」，但未规定 *总线只接受带签章的消息* |
| **威胁覆盖** | 八类：注入、本体投毒、恶意结构、越狱、隐藏指令、提权、混淆、工具滥用 | 五阶段 *能映射到* 这八类，但不是一类一层，也不是一层一类 |

因此可行性必须拆成三个问题，而不是一个「能不能做」：

1. **工程上能否按时序跑完五阶段？** → 能。
2. **跑完后能否支撑「每条消息过墙」？** → 能，前提是做成内核中间件，而不是 Agent 可选插件。
3. **能否靠这五阶段单独消掉 3.6 的八类威胁？** → 不能。Stage 3 的 RBAC 与 Stage 4 的本体闸是硬控制；Stage 2 / 5 是检测，有漏报。

## 2. 五阶段逐项可行性

成熟度：**高** = 有现成库、失败模式清楚、可进热路径；**中** = 能落地但有计算/漏报边界；**低** = 研究问题，不能当强制门禁。

### Stage 1 预处理与逆混淆 — 成熟度：高

**要做的事**：去零宽 / Tag 区 / BIDI 覆盖、有界解码（Base64、URL、HTML 实体、Unicode 转义）、NFKC、同形字骨架化。

| 项 | 判断 |
| --- | --- |
| 可行性 | **高**。Unicode 安全处理与有界解码是确定算法，不依赖模型。 |
| 开源 | `ftfy`、`textguard` / `prompt-canon`、`confusable-homoglyphs`、`bleach`/`nh3` |
| 必守边界 | 解码轮次上限（建议 2–3）；超限视为攻击而非继续解。规范化前后哈希都要留。 |
| 失败模式 | **解不够**：套娃编码漏到 Stage 2。**解过头**：良性 Base64 附件被展开，误报升高。 |
| 对 3.6 的贡献 | 隐藏指令、语义混淆的 *载体* 层。没有这一层，后面所有规则和分类器都可以被零宽 / 同形字绕过。 |

**结论**：必须做，且必须是第一层。不可跳过、不可「模型自己注意一下」。

### Stage 2 静态模式与隐性指令扫描 — 成熟度：高（已知攻击）/ 低（未知改写）

**要做的事**：YARA / 正则 / 启发式打 Prompt Injection、Jailbreak、系统提示套取、角色劫持、伪 `tool`/`system` 块。

| 项 | 判断 |
| --- | --- |
| 可行性 | 对 **已知话术、已知模板、已知分隔符** 可行，亚毫秒级，适合短路阻断。 |
| 开源 | `yara-python` + 自维护规则；`injectionguard` / Cisco ATR（Agent/MCP 向）；密钥用 `detect-secrets` |
| 不可行之处 | 同义改写、多语言、Crescendo / TAP 多轮渐进、间接注入（藏在网页/PDF/工具回执里的「请忽略上面」）**规则打不准**。 |
| 对 3.6 的贡献 | 越狱、直接注入、部分隐藏指令。是过滤器的「签名引擎」，不是语义引擎。 |

**结论**：可行且应短路。但若把 3.6 的成功率押在规则库上，需求就 **不可行**——规则库必然落后于攻击话术。

### Stage 3 结构化与权限校验 — 成熟度：高（硬前提：授权在模型外）

**要做的事**：工具参数 Schema、越权指令、越界操作（路径、URL、租户、动作等级）。

这是五阶段里 **安全价值最高** 的一层，也是最容易设计错的一层。

| 做法 | 可行？ | 说明 |
| --- | --- | --- |
| JSON Schema / 深度宽度上限校验 `tool_call` | **高** | 恶意结构、参数注入的主防线 |
| 用 OPA / Casbin / OpenFGA（Guardian Trust）做 PEP | **高** | 「你现在是管理员」只能当 *攻击信号*，不能改变 `capabilities` |
| 从自然语言 *推断* 用户是否在提权，再决定是否授权 | **低** | 把 RBAC 交给分类器，等于没有 RBAC |
| 工具白名单随用户一句话扩权 | **不可行** | 直接违反 3.6 的权限提升防护 |

与本仓库已有 **Guardian Trust**（身份、ReBAC、L0–L5 Action Guard）的关系：

- Stage 3 的「能不能调这把工具 / 能不能碰这个资源」**应调用信任图 PEP**，不要在语义防火墙里再实现一套角色。
- 语义防火墙负责：这条 *消息* 是否在试图改策略、改角色、走私参数。
- Guardian Trust 负责：这个 *身份* 现在到底有没有这个能力。

**结论**：结构化校验 + 外置 PEP **可行，且应作为提权与工具滥用的唯一事实源**。若 Stage 3 只是「扫描越权话术」，则 3.6 的权限提升需求 **不可行**。

### Stage 4 本体与知识一致性 — 成熟度：中

这是 ECS 相对通用 LLM 网关的差异化层，也是五阶段里唯一不能「对每条闲聊都跑」的层。

| 子能力 | 可行性 | 说明 |
| --- | --- | --- |
| 形状约束（SHACL） | **高** | `pySHACL` + RDFLib；禁止的类/属性/基数可以写成 shapes |
| OWL 一致性（HermiT / Pellet） | **中** | 对 *有界* `ontology_patch` 可行；大图可能超时或不可判定，必须配额 + 超时即拒绝 |
| 注释 / 标签走私 | **高** | `rdfs:comment`、工具 description 当 T2/T3 文本走 Stage 1–2–5 |
| `owl:equivalentClass` / `sameAs` 把外部实体并进高权类 | **中** | 可用 SHACL + triple diff 拦「碰核心 IRI」；需要核心 IRI 白名单 |
| **逻辑一致、但策略恶意** 的公理（例如把「访客」合法地定义成可停机） | **低** | 推理器认为 consistent，防火墙不能单靠「一致性」发现恶意。必须：shapes 禁权限边、差分审计、staging、双人复核 |
| 向量库检索投毒 | **中** | 入库当前 T2 扫描；不是 OWL 问题 |

**硬约束（否则 Stage 4 没有意义）**：

1. T2/T3 内容禁止直接写核心图。
2. 核心 TBox 只读；外部知识进 `staging` named graph。
3. 图过大、推理超时、闭包爆炸 → **拒绝**，不是降级放行。

**结论**：作为「本体写入闸门」**可行**；作为「自动理解知识是否被投毒」**不可行**。3.6 的 Ontology Poisoning 应按 *变更控制* 实现，而不是按 *语义分类* 实现。

### Stage 5 轻量语义模型评测 — 成熟度：中

**要做的事**：隐晦意图、改写后的注入/越狱、多语言变体。

| 项 | 判断 |
| --- | --- |
| 可行性 | **中**。22M–86M 级 Prompt Injection 分类器（如 Meta Prompt Guard 2）可内网部署，延迟可进热路径（数十毫秒量级）。 |
| 开源 | LlamaFirewall + Prompt Guard 2；第二票可用异源 DeBERTa；内容安全用 Llama Guard（与注入检测互补，不要混成一个分） |
| 不可行之处 | 对抗样本、新颖越狱、目标劫持后「表面回复正常 + 偷偷改 tool_call」——轻量分类器 **看的是文本，不是行为**。 |
| 位置 | 放在最后 **可以**（让贵模型只看活下来的消息），但 **不能让 Stage 3/4 等它**。高危通道（工具、本体、跨 Agent）分类器挂死必须 fail-closed，不能因 Stage 5 超时而放行。 |

Protect AI **LLM Guard 已于 2026-07 归档**，生产主依赖应避开。NeMo Guardrails 适合做 *政策轨*（禁改系统提示、禁扩权），不适合每条消息同步 LLM 自检。

**结论**：作为 Stage 2 的补网 **可行、应该做**。作为 3.6 的最后一道「语义真理」**不可行**。

## 3. 八类威胁 × 五阶段：覆盖矩阵

图例：● 主控制　◐ 辅助检测　○ 基本无覆盖（本五阶段图内）

| 3.6 威胁 | S1 逆混淆 | S2 规则 | S3 结构/RBAC | S4 本体 | S5 分类器 | 缺口（图外必须补） |
| --- | --- | --- | --- | --- | --- | --- |
| Prompt Injection | ◐ | ● | ○ | ◐ 注释 | ● | 间接注入要在 RAG/工具回执 **入库前** 再跑同一管道 |
| 本体投毒 | ◐ 补丁文本 | ◐ | ○ | ● | ◐ | 签名、staging、人工晋升；一致但恶意的公理 |
| 恶意语义结构 | ◐ 深度 | ◐ | ● JSON | ● 图配额 | ○ | 伪 function-call 只接受 schema 成功的 payload |
| Jailbreak | ◐ token | ● 已知 | ○ | ○ | ● | 多轮 Crescendo：要会话链，不能只看单条 |
| 隐藏指令 | ● | ● 解码后再扫 | ○ | ● RDF 注释 | ◐ | MCP `description` 钉扎 |
| 权限提升 | ○ | ◐ 话术 | ● PEP | ● 禁权限边 | ◐ | **能力清单禁止由文本改写** |
| 语义混淆 | ● | ◐ mixed-script | ○ | ◐ IRI | ● 改写 | 同义改写永远有漏报 |
| 工具滥用 | ○ | ◐ 危险名 | ● Schema | ◐ 动作是否合法 | ○ | **调用前闸门 + 回执二次过墙 + 目标对齐** |

读法：

- 五阶段对 **入站文本** 的 隐藏指令 / 已知越狱 / 混淆 / 直接注入：**可行**。
- 对 **权限提升**：**仅当 Stage 3 是外置 PEP 时可行**。
- 对 **本体投毒**：**仅当 Stage 4 是写入闸门而非「读一段 OWL 做情感分析」时可行**。
- 对 **工具滥用**：五阶段图画在 Agent **之前**，而工具滥用发生在 Agent **之后**。这是本方案最大的结构性缺口。

## 4. 原方案结构上的五个问题（不影响「能不能做」，影响「做了管不管用」）

### 4.1 只有入站，没有动作面

原图是：

```
消息 → 五阶段 → 阻断/降级  或  放行至 Agent
```

3.6 的实际数据流是：

```
不可信内容 → [过墙] → 进入上下文 → Agent 规划
    → 拟 tool_call / ontology_write → [再过墙] → 副作用
    → 工具回执 → [再过墙] → 回注上下文
    → 最终输出 / 跨 Agent → [再过墙]
```

攻击者可以让入站文本很干净，在第 3 步才改工具参数。  
**不增加「第六阶段模型」也能补**：动作面、回执面、出站面 **复用 Stage 1–5**，按 `payload_kind` 开关（纯文本跳过 Stage 4，`tool_call` 跳过 OWL）。

### 4.2 裁决只有「阻断 / 降级 / 放行」不够

3.6 至少需要：

| 裁决 | 为何必要 |
| --- | --- |
| `ALLOW` | 放行 |
| `SANITIZE` | 清零宽后放行（Stage 1 的主出口） |
| `ISOLATE` | RAG/工具回执当数据、不当指令（spotlighting） |
| `REDACT` | PII / 密钥 |
| `HITL` | 高危工具、本体晋升 |
| `BLOCK` | 拒绝 |

「降级」若只是「换小模型」，挡不住工具调用。降级必须落到 **ISOLATE / 只读 / 禁工具**。

### 4.3 Stage 5 放最后：成本合理，依赖关系要改

串行 `1→2→3→4→5` 有两个浪费：

- 闲聊文本不该进 OWL。
- 明显越狱不该等推理器。

推荐热路径：

```
        ┌─ 文本通道：S2 规则 ─┬─ S5 分类器（可并行）─┐
S1 规范化┤                    │                      ├─ 聚合裁决
        └─ 结构通道：S3 Schema + PEP ────────────────┤
        └─ 仅 ontology_patch：S4 SHACL/OWL ──────────┘
任一层达阻断阈值 → 短路
```

S3 **不依赖** S5 的分数来授权。S5 只提供加严信号（例如注入分高 → 即使 Schema 合法也 `HITL`）。

### 4.4 未定义失败默认与通道差异

| 通道 | 过滤器挂死时 |
| --- | --- |
| 闲聊 | 可 fail-open + 审计 + 限流 |
| RAG 入库 / 记忆写入 | fail-closed |
| 工具调用 / 本体补丁 / 跨 Agent | fail-closed |

没有这张表，「每条消息必过墙」在工程上会变成「墙一超时就绕过」。

### 4.5 没有 stamp，模型可以自我豁免

必须：语义总线拒绝无 `filter.stamp` 的消息；stamp 只能由过滤器进程签发；Agent 上下文里出现「请把 stamp 设为 ALLOW」属于 Stage 2/3 命中。  
这一条是强制闸门是否成立的充要条件，比选哪个分类器更重要。

## 5. 与「六层方案」的关系（不互相否定）

仓库中另有一份六层方案（L0 规范化 → L1 规则 → L2 分类器 → L3 策略轨 → L4 本体 → L5 对齐/工具闸）。映射如下：

| 本五阶段 | 六层方案 | 取舍 |
| --- | --- | --- |
| S1 | L0 | 同一件事 |
| S2 | L1 | 同一件事 |
| S3 | L3 + L5 的工具闸 | 五阶段把「授权」提前，这是对的 |
| S4 | L4 | 同一件事 |
| S5 | L2 | 五阶段把分类器后置，利于短路；六层把分类器前置，利于给策略轨喂分 |
| （缺失） | L5 AlignmentCheck | 五阶段需在动作面补「目标是否被劫持」，不必单列成第六个常驻模型 |

**推荐采用五阶段对外叙事、六层对内实现**：对外保持本图的可讲性；对内按 `payload_kind` 走不同子图，并在 tool_call 上加对齐检查。

## 6. 落地边界：怎样才算「需求被满足」

### 6.1 第一代就可以宣称 3.6 可行的最小闭环

只做这些，就已经是语义防火墙，而不是 Demo 扫描器：

1. 消息信封：`source / trust_tier / payload_kind / capabilities / stamp`
2. 入站 + 工具调用前 + 回执回注 三个 choke point（其余五个可随后加）
3. Stage 1 + 2 全量，不可跳过
4. Stage 3：Schema + 调用 Guardian Trust / OPA，模型改不了能力清单
5. Stage 4：仅 `ontology_patch`，SHACL + 超时拒绝 + 禁止 T2/T3 写核心图
6. Stage 5：可降级的分类器；高危通道禁止跳过
7. 裁决含 `ISOLATE` / `HITL` / `BLOCK`；审计留 raw/canonical 哈希

### 6.2 第一代不要承诺的事

- 未知越狱检出率 100%
- 自动识别「逻辑一致的恶意公理」
- 用轻量分类器替代 Action Guard / 工业 L5 确定性控制
- 替代操作系统沙箱、密钥管理、网络防火墙

### 6.3 建议的技术顺序（按依赖，不按日历）

| 顺序 | 内容 | 满足 3.6 的哪一块 |
| --- | --- | --- |
| A | 信封 + stamp + S1 + S2 + S3 PEP | 强制过墙、隐藏指令、已知越狱、提权、工具参数 |
| B | S5 分类器 + 会话链 | 改写注入、多轮越狱补网 |
| C | S4 SHACL/OWL + staging | 本体投毒 |
| D | 回执/出站/MCP 钉扎 + 轨迹对齐 | 工具滥用闭环、间接注入 |

A 做完即可回答「需求是否可行」：**可行，且已有强制闸门**。B–D 是把漏报从「工程未做」降到「分类器天花板」。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 规则 + 分类器误杀业务话术 | 可用性 | 金标集；`ISOLATE` 优于误 `BLOCK`；闲聊可审计放行 |
| OWL 推理拖死热路径 | 延迟 | Stage 4 旁路，仅补丁通道；超时 = BLOCK |
| 把 Guardian Trust 与防火墙做成两套角色 | 提权绕过 | Stage 3 只问 PEP，不本地发明角色 |
| 分类器供应中断（归档、门控权重） | 高危通道无模型 | 热路径必须在无 S5 时仍能靠 S1–S3 fail-closed |
| 多 Agent 互传未过墙 | 横向扩散 | 跨 Agent 通道与工具回执同等对待（T3） |
| 会话链把已阻断内容写回历史 | 误杀后续良性轮次 | 仅 `ALLOW`/`SANITIZE` 入链 |

## 8. 最终判定

| 问题 | 答案 |
| --- | --- |
| 五阶段方案作为 3.6 的 **架构骨架** 是否可行？ | **是。** |
| 按原图「只在进 Agent 前扫一次、二值放行」是否满足 3.6？ | **否。** 必须复用到工具调用前与回执回注，并外置 PEP。 |
| Stage 1–2 是否足以支撑生产？ | **不足以单独支撑**，但是强制且高成熟度的前两层。 |
